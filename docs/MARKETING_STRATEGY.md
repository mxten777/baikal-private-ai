## 3. 상용화 갭 분석

> MVP → 첫 납품 → 상용 제품으로 올라가는 데 필요한 보완 항목 목록

### ✅ 이미 상용화 수준인 것

- RAG 파이프라인 (하이브리드 검색 + Cross-encoder + MMR + HyDE)
- 3단계 RBAC + 문서별 접근 권한 제어
- JWT 인증 + Refresh Token 블랙리스트
- SSE 스트리밍 응답
- 감사 로그 (QueryLog + KPI)
- Docker 단일 명령 배포
- HWP/HWPX/PDF/DOCX/XLSX 파일 처리
- 신뢰도 sigmoid 절대 관련도 + 출처 청크 미리보기

---

### 🚧 상용화에 필요한 보완 항목

#### 1순위 — 안정성 / 보안 (파일럿 납품 전 필수)

| 항목 | 현재 상태 | 필요 조치 |
|------|:---------:|-----------|
| HTTPS/TLS | ❌ HTTP만 | Let's Encrypt 또는 기업 인증서 적용 |
| 비밀번호 정책 | ❌ 없음 | 복잡도 강제 + 만료 주기 설정 |
| Rate Limiting | ❌ 없음 | IP/사용자별 분당 요청 제한 |
| DB 백업 | ❌ 없음 | 자동 pg_dump + 볼륨 스냅샷 스크립트 |

#### 2순위 — 운영 (계약 이후 3개월 내)

| 항목 | 현재 상태 | 필요 조치 |
|------|:---------:|-----------|
| 모니터링 | ❌ 없음 | Prometheus + Grafana 또는 경량 대안 |
| 로그 집계 | Docker logs만 | 파일 로테이션 + 중앙 수집 |
| 다중 사용자 부하 | 단일 4-Worker | GPU 서버 또는 수평 확장 구성 |
| 설치 자동화 | 수동 명령어 | 비개발자용 설치 스크립트/인스톨러 |

#### 3순위 — 제품화 (2번째 고객 이후)

| 항목 | 현재 상태 | 필요 조치 |
|------|:---------:|-----------|
| 라이선스 관리 | ❌ 없음 | 고객사별 활성화 키 발급 체계 |
| 멀티테넌시 | ❌ 단일 DB | 고객사별 스키마 분리 (선택적) |
| 관리자 대시보드 | 기본 통계 | 사용량·비용 추이 차트 |
| 온보딩 UI | ❌ 없음 | 최초 설정 마법사 |

---

### 결론

```
1순위 보완 (2~4주)  →  파일럿 납품 가능
2순위 보완 (1~2개월) →  유료 계약 갱신 가능
3순위 보완 (3개월+)  →  멀티 고객 운영 가능
```

> **버티컬 SaaS 형태라면 1순위만 보완해도 첫 고객 납품 가능하다.**  
> 공공/금융처럼 보안 인증이 필요한 시장은 CC인증·망분리 요건이 추가된다.

## 4. 지금 해야 할 전략 3가지

### 전략 1 — 공공기관 법령 버티컬로 첫 PoC를 확보한다

**왜 공공인가:**

| 항목 | 공공기관 | 민간 법무팀 |
|------|---------|------------|
| 조달 경로 | 나라장터 공개입찰 (레퍼런스 없어도 가능) | 콜드 영업 필요 (레퍼런스 必) |
| 정답 검증 | 법령 조문은 객관적으로 맞고 틀림이 명확 | 계약서 해석은 주관 개입, 리스크 큼 |
| HWP 강점 | 공공기관 = HWP 비율 최고 | 대기업 법무 = PDF 혼용 |
| 예산 구조 | 연간 정보화 예산 확보 | 독립 예산 집행 불확실 |
| 레퍼런스 복사 | A 지자체 성공 → B 지자체 동일 패키지 | 업종마다 재입증 필요 |

**첫 타깃**: 기초자치단체(시·군·구) 행정 내규 검색 AI
- 조례 + 내부 결재 규정 + 업무 매뉴얼: HWP 비율 80% 이상
- 담당자 1~2인이 의사결정 → 절차 복잡도 낮음
- 예산 규모: PoC 1,000~2,000만원 → 충분히 빠른 계약 가능

---

### 전략 2 — 파트너 채널 1개를 선택해서 집중한다

**직접 영업의 현실:**
- 공공기관은 SI 업체를 통해 도입 → 콜드 영업은 대부분 차단
- 제조기업은 구매팀 프로세스가 6개월 이상
- 1인 운영이라면 개발 + 영업 + 지원 동시 불가능

**권장 파트너 유형:**

| 파트너 유형 | 접근 방법 | 활용 강점 |
|------------|----------|----------|
| 중소 SI / 공공 IT 업체 | BAIKAL을 솔루션으로 번들하는 OEM 제안 | 기존 공공 고객 채널 보유 |
| 한글과컴퓨터 협력 | HWP 파싱 협력 + 파트너십 | "한글 AI"로 공동 마케팅 |
| 공공 클라우드 업체 | NCloud, KT Cloud 마켓플레이스 등록 | 공공기관 신뢰도 확보 빠름 |

> **선택지를 3개 다 추구하지 말고, 하나만 골라 3개월 집중한다.**

---

### 전략 3 — 데모 패키지와 ROI 계산기를 먼저 만든다

**현재 없는 것 (기술보다 중요한 것):**

1. **업종별 샘플 문서셋** — "이 문서를 BAIKAL에 넣으면 이런 질문에 이렇게 답한다"는 시연 패키지가 없다
2. **ROI 계산기** — "현재 담당자 X명이 문서 검색에 Y시간 → BAIKAL 도입 후 Z% 절감"을 수치로 보여주지 못한다
3. **설치 가이드 (비개발자용)** — 지금은 Docker를 아는 사람만 설치 가능. 담당 공무원이 설치할 수 없다

이 3가지는 기술 개발보다 **1인 기준 2주 이내에 만들 수 있다**.  
이것이 없으면 아무리 기술이 좋아도 PoC 미팅 이후 진척이 없다.

## 5. 첫 고객 확보 실행 경로

### "레퍼런스가 없어서 고객을 못 잡는" 루프를 끊는 방법

```
문제:  레퍼런스 없음 → 고객 안 줌 → 레퍼런스 없음 (무한 루프)

해결:  무료 PoC → 성공 사례 작성 권리 확보 → 레퍼런스로 활용
```

**단계별 실행:**

```
1단계 — 무료 PoC 제안 (4~6주)
│
├─ 대상: 지인 네트워크 중 공공기관/지자체 종사자 1명
│        또는 중소기업 법무/총무팀 담당자 1명
│
├─ 조건: 무료 설치 + 운영 지원
│        대신 "도입 후기 사례 작성" 동의 받기
│
└─ 목표: 실사용 데이터 3개월치 확보

2단계 — 레퍼런스 기반 입찰 (3개월~)
│
├─ 나라장터 "AI 도입" 관련 제안요청서(RFP) 모니터링
├─ 첫 PoC 기관의 이름 게재 허락 확보
└─ 제안서에 "OO 기관 실증 완료" 표기

3단계 — 복사 영업 (6개월~)
│
└─ 같은 업종/규모 기관에 동일 패키지 제안
   (공무원 네트워크는 같은 업무 담당자끼리 정보 공유가 빠름)
```

## 6. 하지 말아야 할 것

| 하지 말아야 할 행동 | 이유 | 대안 |
|---------------------|------|------|
| 버티컬 3개 동시 개발 | 집중력 분산, 임시 모든 것이 50% 완성도 | 법령 버티컬 하나만 먼저 완성 |
| 계약서 AI로 법무팀 콜드 영업 | 레퍼런스 없이 법무팀 미팅은 성사 안 됨 | 파트너 채널로 접근 |
| "더 좋은 기능" 개발에 집중 | 기술은 이미 충분하다 | GTM(고객 확보 경로)에 집중 |

| 가격 낮추기 경쟁 | 낮은 가격 = 낮은 신뢰도 (공공기관 심리) | ROI 근거로 가격 방어 |

## 1. 현재 포지션의 한계

BAIKAL은 현재 **"모든 문서를 처리하는 폐쇄망 RAG 플랫폼"** — 수평 플랫폼 포지션이다.

| 항목 | 현황 |
|------|------|
| 지원 파일 형식 | PDF, DOCX, XLSX, HWP, HWPX |
| 검색 방식 | 하이브리드 (벡터 + 키워드) + Cross-encoder Reranking |
| 배포 형태 | 폐쇄망 Docker 단일 패키지 |
| 타겟 고객 | 기업 일반 (업종 무관) |

**수평 플랫폼의 문제점**:
- TAM은 크지만 "우리 업무에 딱 맞는 솔루션"이라는 인식을 주기 어렵다
- 도입 결정이 느리다 — PoC → IT팀 검토 → 예산 → 계약 (6~12개월)
- "범용 RAG가 왜 비싸야 하나"는 가격 저항에 취약하다
- ChatGPT Enterprise, Microsoft Copilot 등 대형 벤더와 직접 비교 당한다

## 2. 왜 버티컬 특화인가

### 수평 vs 수직 비교

| 구분 | 범용 RAG (현재) | 수직 특화 RAG (목표) |
|------|----------------|---------------------|
| 영업 사이클 | 6~12개월 | 1~3개월 |
| 가격 저항 | 높다 ("왜 비싸?") | 낮다 ("업무 줄이면 본전") |
| 경쟁 강도 | 매우 높다 (범용 다수) | 낮다 (도메인 특화 희소) |
| 재계약율 | 낮다 | 높다 (업무 프로세스에 내재화) |
| 레퍼런스 효과 | 약하다 | 강하다 ("계약서 AI 도입 사례") |
| ROI 설명 | 추상적 | 구체적 (계약 검토 시간 X시간 → Y분) |

### 폐쇄망 요건과 버티컬의 궁합

계약서·법령·견적서는 모두 **외부 유출이 가장 엄격히 통제되는 문서**다.  
ChatGPT/Claude에 계약서 원문을 붙여넣는 것은 기밀 유출 위험 → **폐쇄망 RAG 수요가 가장 강한 영역**이기도 하다.

> "폐쇄망"과 "버티컬 특화"는 같은 고객을 가리킨다.

## 3. 추천 버티컬 3개

### 3-1. 계약서·법무 (1순위)

**왜 1순위인가?**
- 법무팀/구매팀은 독립 예산 집행 권한 보유 — IT팀 승인 불필요
- ROI 즉각적: 계약 검토 1건당 평균 2~4시간 → AI 보조 30분 이내
- 기밀성 요구가 가장 강해 폐쇄망 선호도 최고

**타겟 고객**:
- 중견~대기업 법무팀 (계약서 검토 업무량 많음)
- 스타트업 대표/CFO (법무 인력 없이 계약서 리뷰)
- 법무법인 내부 지식 관리

**특화 기능 (현재 코드 위에 추가)**:
- 조항 번호 기반 청킹 (`제X조`, `Article X` 단위)
- 의무사항·금지사항·기한 자동 추출
- 계약서 간 조항 비교 (버전 관리)
- 만료일·갱신일 알림 메타데이터

**킬러 질문 예시**:
```
"이 계약서에서 손해배상 한도 조항을 찾아줘"
"계약 기간이 언제까지이고 자동 갱신 조건은?"
"을이 부담하는 의무사항을 전부 나열해줘"
"이전 계약서와 달라진 조항이 뭐야?"
```

---

### 3-2. 법령·조례 (2순위)

**왜 2순위인가?**
- 공공 시장: 예산 확보가 구조적으로 쉽다 (정보화 예산, 디지털뉴딜)
- 계약 규모 크다 (지자체 1개 = 억 단위)
- 법령 개정이 잦아 최신성 유지 수요가 있음

**타겟 고객**:
- 지방자치단체 (조례 해석 질의응답)
- 행정기관 (내부 훈령·예규 검색)
- 규정 준수(Compliance) 담당 부서

**특화 기능**:
- 상위법/하위법 계층 구조 청킹
- 개정 이력 추적 (문서 lineage — 이미 0007 migration 완료)
- 조문 번호·항·호 단위 정밀 청킹
- "○○조에 의하면" 출처 인용 형식 강화

**킬러 질문 예시**:
```
"주민등록법 제17조의 내용은?"
"이 사업이 어떤 조례의 적용을 받나요?"
"작년 대비 개정된 조항은 무엇인가요?"
```

---

### 3-3. 견적서·품의서·발주서 (3순위)

**왜 3순위인가?**
- 제조·건설·유통 업종의 핵심 문서
- ERP에 없는 비정형 데이터 영역 (ERP는 정형 데이터만)
- 수량·단가·납기 등 숫자 데이터 추출이 핵심

**타겟 고객**:
- 제조업 구매/발주 담당자
- 건설사 원가 관리팀
- 유통업 계약·정산 담당자

**특화 기능**:
- 표/숫자 추출 정확도 강화 (XLSX 처리 이미 검증 완료)
- 업체별·품목별 단가 비교
- 납기 준수율 추적
- 견적 이력 비교 ("작년보다 얼마 올랐나")

**킬러 질문 예시**:
```
"A업체의 품목별 단가를 정리해줘"
"이번 분기 발주 총액이 얼마야?"
"납기를 못 지킨 계약건을 찾아줘"
```

## 4. 기술 구현 방향

### 핵심 원칙: 같은 엔진, 다른 설정

**현재 아키텍처를 재작성할 필요 없다.**  
버티컬별로 3가지 레이어만 커스터마이징:

```
BAIKAL Core (현재 코드 — 그대로 유지)
├── 범용 모드          ← 현재
├── 계약서 모드        ← 프롬프트 + 청킹 전략 변경
├── 법령 모드          ← 계층 구조 청킹 + 메타데이터
└── 견적서 모드        ← 숫자/표 추출 강화
```

### 버티컬별 커스터마이징 항목

| 레이어 | 범용 | 계약서 | 법령 | 견적서 |
|--------|------|--------|------|--------|
| **청킹 전략** | 문단 단위 | 조항 단위 | 조문 단위 | 시트/표 단위 |
| **청크 크기** | 512 token | 256 token (짧은 조항) | 384 token | 가변 (표 크기) |
| **메타데이터** | 페이지, 파일명 | 조항번호, 만료일 | 조문번호, 개정일 | 품목, 단가, 납기 |
| **시스템 프롬프트** | 일반 QA | 법률 용어 정확성 강조 | 조문 인용 형식 | 숫자/수치 정확성 강조 |
| **출처 표시** | 파일명 + 유사도 | 계약서명 + 조항번호 | 법령명 + 조문번호 | 견적서명 + 품목 |

### 코드 변경 규모 (추정)

- 청킹 전략: `chunker.py` 버티컬 프로파일 추가 (~200줄)
- 메타데이터 추출: `loader.py` 도메인별 파서 추가 (~300줄)
- 프롬프트 관리: `rag_service.py` 프로파일 분기 (~100줄)
- UI: 문서 업로드 시 "문서 유형" 선택 드롭다운 추가

**총 추가 개발 공수: 약 2~3주 (1인 기준)**

- 계약서 AI로 민간 법무팀을 첫 고객으로 삼는 전략은 실행 경로와 리스크 관리가 명확하지 않으면 **6개월을 낭비할 수 있다**

## 2. 진짜로 작동하는 강점

### 폐쇄망 × 버티컬의 궁합

이 전략에서 가장 강력한 부분이다.

- 계약서/법령 문서는 외부 유출 통제가 가장 엄격한 문서
- 폐쇄망 + 버티컬 특화를 동시에 충족하는 제품은 국내에 드물다
- ChatGPT/Claude로 계약서 원문을 분석하는 기업 법무팀은 사실상 없다 → **수요가 실재하는 시장**

### HWP 지원의 실질적 차별화

- 공공기관·법무법인 기준 계약서/규정 원본이 HWP인 경우가 지금도 흔하다
- 대부분의 외산 RAG 솔루션이 여기서 막힌다
- 단순 기술 특징이 아닌 **실제 영업 포인트**로 작동한다

---

## 3. 치명적 약점 3가지

### 3-1. 계약서 버티컬 — 할루시네이션 리스크가 버티컬 선택 자체를 위협한다

가장 큰 문제다.

법무팀이 "손해배상 한도 조항 찾아줘"라고 물었는데 AI가 **틀린 조항을 틀린 내용으로 제시**하면?

| 문제 | 설명 |
|------|------|
| 모델 한계 | qwen2.5:7b 로컬 모델 기준 계약서 법률 용어 해석 정확도 보장 어려움 |
| 용도 혼동 | BAIKAL은 "검색"이지만 고객은 "검토"로 사용할 가능성 있음 |
| 책임 구조 | 법적 오류 발생 시 공급자 책임 범위 불명확 |
| 심리적 저항 | 법무팀은 이 리스크를 이미 알고 있어 도입 결정을 매우 조심스럽게 함 |

> **결론**: 계약서 버티컬 1순위 판단은 재검토가 필요하다. ROI 설명이 쉬운 만큼 **실수의 비용도 크다**.

---

### 3-2. "법무팀이 독립 예산 집행"이라는 전제가 틀렸다

전략 문서의 핵심 전제:
> *"법무팀/구매팀은 독립 예산 집행 권한 보유 — IT팀 승인 불필요"*

이 전제는 **대기업 일부에만 해당하는 예외적 케이스**다.

| 기업 규모 | 실제 구매 경로 |
|-----------|----------------|
| 대기업 | 법무팀 → IT 보안팀 → 구매팀 → 계약 (6~9개월) |
| 중견기업 | 법무팀 건의 → 경영진 → IT → 구매 (3~6개월) |
| 스타트업 | CEO 직접 결정 (빠르지만 예산이 작다) |
| 법무법인 | 파트너 동의 없이 IT 인프라 도입 불가 |

전략 문서의 "영업 사이클 1~3개월"은 **현장 기준으로 낙관적**이다.

---

### 3-3. 첫 앵커 고객 확보 경로가 없다

전략 문서 어디에도 **"어떻게 첫 고객을 만날 것인가"** 가 없다.

- 법무팀은 콜드 영업에 반응하지 않는다
- 계약서 AI 시연 자료를 들고 법무팀 미팅을 성사시킬 네트워크가 있는가?
- 레퍼런스 없이 계약서·법령을 다루는 기관에서 PoC 기회를 주지 않는다
- **"레퍼런스가 없어서 첫 고객을 못 잡고, 첫 고객이 없어서 레퍼런스가 없는" 구조**

---

## 4. 버티컬 순위 재평가

| 버티컬 | 전략서 순위 | 냉정한 재평가 | 이유 |
|--------|-------------|---------------|------|
| 계약서·법무 | 1순위 | **3순위** | 할루시네이션 리스크 × 법적 책임 × 영업 경로 부재 |
| 법령·조례 | 2순위 | **1순위** | 공공 조달 경로 존재, 정답 검증 가능, HWP 강점 직결 |
| 견적서·품의서 | 3순위 | **2순위** | ERP 없이도 독립적 가치, 숫자 정답/오답 명확 |

### 법령 버티컬을 1순위로 올려야 하는 이유

1. **검증 가능성**: "제17조 제2항"이라는 답은 맞고 틀림이 명확 → 할루시네이션 검증 가능
2. **진입 경로**: 공공 조달(나라장터, 정보화전략계획)은 레퍼런스 없이 입찰 가능한 경우 존재
3. **복사 영업**: 지자체 한 곳 시범사업 성사 시 유사 지자체 복사 영업 가능
4. **HWP 직결**: 공공기관 HWP 의존도가 민간보다 훨씬 높아 BAIKAL의 HWP 지원이 직접 차별화

---

## 5. 진짜 위험 요소

### 경쟁사가 이미 움직이고 있다

- 국내 AI 스타트업 중 계약서 AI를 명시적으로 하는 곳들이 2025~2026년 사이 등장했다
- 삼성SDS, SK C&C 같은 SI 업체들도 폐쇄망 RAG 구축 사업을 수주 중이다
- **2~3주 개발 격차는 경쟁 우위가 아니다**

### 기술이 아니라 영업이 병목이다

- 개발 1인 기준이라면 버티컬 MVP 개발 2~3주 후 영업에 집중할 수 있는 시간과 채널이 있는가?
- 기술 완성도를 높여도 **영업 채널이 없으면 시장경쟁력은 없다**
- 제품이 준비된 것과 시장이 반응하는 것은 다른 문제다

## 6. 시장경쟁력 최종 판정

| 항목 | 판정 | 비고 |
|------|------|------|
| 전략 방향성 | ✅ 맞다 | 버티컬 전환 자체는 올바른 판단 |
| 버티컬 순위 (현재) | ⚠️ 재검토 필요 | 계약서 1순위는 리스크 과소평가 |
| 기술 기반 | ✅ 실작동 제품 있음 | 파일럿 납품 가능한 수준 |
| 폐쇄망 차별화 | ✅ 진짜 차별화 | 외산 솔루션과 실질적 분리 |
| 첫 고객 확보 경로 | ❌ 전략에 없음 | **치명적 공백** |
| 할루시네이션 리스크 관리 | ❌ 계획 없음 | 계약서 버티컬 진출 시 필수 |
| 가격 경쟁력 (SaaS) | ⚠️ 높은 편 | 국내 중견기업 기준 부담 가능성 |
| 1인 실행 가능성 | ⚠️ 제한적 | 개발은 가능, 영업은 별도 자원 필요 |

### 최종 판단

> **공공기관 법령 버티컬에서는 시장경쟁력이 있다.**
> 폐쇄망 + HWP + 법령 조합은 국내 시장에서 실제로 빈 자리다.
>
> **그러나 지금 당장 계약서 AI 민간 법무팀 영업을 시작하면 6개월을 낭비할 수 있다.**
> 기술이 아니라 "PoC를 허락해줄 기관 한 곳"을 찾는 것이 전략 전체의 병목이다.

## 7. 기술 충분함을 어필하는 방법

**기술은 이미 충분하다. 문제는 그것을 증명하는 자료가 없다는 것이다.**

### 7-1. 수치로 말한다 — RAG 평가 지표 공개

`scripts/eval_rag.py`가 이미 구현되어 있다. Precision@K, Recall@K, MRR, nDCG@K, Reranking Lift를 자동 산출한다.

```powershell
python scripts/eval_rag.py --testset scripts/eval_testset.json --k 5 --mode hybrid
```

이 결과를 제안서 첫 페이지에 넣는다:

| 지표 | 측정값 | 의미 |
|------|--------|------|
| Precision@5 | (측정) | 상위 5개 중 관련 문서 비율 |
| Reranking Lift | (측정) | Cross-encoder 적용 전후 정확도 향상폭 |
| 평균 응답 지연 | (측정) | CPU 환경 기준 |

> 경쟁사는 이 수치를 공개하지 않는다. **숫자가 있다는 것 자체가 차별화다.**

### 8-2. "RAG 전문 비교 사이트"는 없다 — 이것이 오히려 기회다

**솔직한 현황**: 2026년 현재 "폐쇄망 RAG 솔루션만 전문으로 비교하는 중립 사이트"는 존재하지 않는다.
G2·Capterra에도 국내 폐쇄망 RAG 카테고리 자체가 없다.

→ **BAIKAL이 직접 비교 콘텐츠를 만들면 이 분야 검색 상위를 선점할 수 있다.**

```
기술 비교 블로그 작성
("BAIKAL vs Dify — HWP 문서 처리 실전 비교")
        ↓
네이버 블로그 / 개발자 커뮤니티 공유
        ↓
구글/네이버 검색 "폐쇄망 RAG 비교" 상위 노출
        ↓
PoC 문의 인바운드 발생
```

**콘텐츠 작성 원칙**: "우리가 제일 잘 한다"가 아니라 "같은 조건에서 어떻게 다른지"를 객관적으로 서술한다. 약점도 솔직히 쓰는 것이 기술 독자에게 신뢰를 얻는다.

> **목표**: 엔터프라이즈 규모(수백 사용자, 수만 문서) 대응

| ID | 항목 | 내용 |
|----|------|------|
| P5-1 | **임베딩 캐시** | Redis에 `{text_hash: embedding}` 캐시 → 동일 문서 재업로드 시 임베딩 재생성 불필요 |
| P5-2 | **비동기 임베딩 배치** | 청크 100개를 5개씩 배치 병렬 요청 → 대용량 문서 처리 속도 5~10배 향상 |
| P5-3 | **pgvector HNSW 인덱스** | 현재 ivfflat → HNSW 전환 → 검색 지연시간 50% 단축 (100만 벡터 기준) |
| P5-4 | **문서 버전 관리** | Document Lineage 기반 v1→v2 버전 추적, 구버전 청크 자동 비활성화 |
| P5-5 | **멀티 테넌시** | `organization_id` 기반 데이터 격리 → SaaS 전환 기반 |

### Phase 6 — AI 고도화 (6~12개월)

> **목표**: RAG 품질 정점 + 차세대 AI 기능으로 경쟁사 격차 유지

| ID | 항목 | 내용 |
|----|------|------|
| P6-1 | **Self-RAG** | LLM이 검색 필요 여부를 스스로 판단 (Retrieval On-demand) → 단순 질문 응답속도 70% 단축 |
| P6-2 | **RAPTOR 계층 청킹** | 청크 → 요약 → 요약의 요약 트리 구조 → 전략 문서, 장문 보고서 이해도 향상 |
| P6-3 | **Graph RAG** | 문서 간 엔티티 관계 그래프 → "A 규정이 B 정책에 미치는 영향" 같은 복합 질의 처리 |
| P6-4 | **Fine-tuning 파이프라인** | 고객 문서 기반 LoRA fine-tuning → 도메인 특화 용어 인식 강화 |
| P6-5 | **음성 인터페이스** | STT(Whisper) + TTS 연동 → 현장 근무자(공장, 현장) 음성 질의 지원 |
| P6-6 | **GPU 자동 스케일링** | CPU 모드 유지하되 GPU 노드 추가 시 자동 offload → Kubernetes HPA 연동 |

## 3. 시장경쟁력 분석

### 3.1 현재 포지셔닝

```
              높은 보안/폐쇄망
                    ↑
                    │
     [BAIKAL]  ●   │
                    │
낮은 RAG 품질 ───────┼─────── 높은 RAG 품질
                    │
                    │   [Microsoft Copilot]
                    │   [Google Vertex AI RAG]
                    ↓
              낮은 보안/클라우드 의존
```

**BAIKAL의 차별화 영역**: 폐쇄망 + 높은 RAG 품질을 동시에 달성한 유일한 국산 제품

### 3.2 타겟 시장 규모

| 시장 | 규모 (국내) | 근거 |
|------|------------|------|
| 공공기관 AI 도입 | ~3,400억원/년 (2026) | 디지털플랫폼정부 예산 |
| 금융/보험 RegTech AI | ~1,200억원/년 | FSC 금융혁신 로드맵 |
| 제조 스마트공장 AI | ~2,800억원/년 | 산업부 스마트제조 정책 |
| 의료/제약 문서 AI | ~900억원/년 | 보건복지부 디지털 전환 |
| **합계 (타겟 세그먼트)** | **~8,300억원/년** | |

### 3.3 핵심 강점 (Value Proposition)

#### ① 완전 폐쇄망 — 데이터 주권 보장
- 외부 API 호출 **0건** (Ollama 완전 로컬)
- 망분리 환경(국방, 금융, 공공) 그대로 설치 가능
- CSAP(클라우드 보안인증) 취득 경로 열려있음

#### ② 한국어 문서 네이티브 처리
- **HWP/HWPX 네이티브 파서** — 경쟁사 전부 미지원
- 한국어 BGE-M3 임베딩 (다국어 최고 성능)
- 한국어 2-gram 토크나이저 내장 BM25

#### ③ Enterprise-grade 신뢰 아키텍처
- 출처 100% 추적 (청크 → 문서 → 페이지 번호)
- 감사 로그 + RBAC + Zero Trust (토큰 폐기)
- Guardrail + Policy Violation 기록

#### ④ 검색 품질 최상위 구조
```
Vector (70%) + BM25 (30%) → MMR (다양성) → Cross-encoder (정밀도) → HyDE (선택)
```
- BM25 + Vector Hybrid: Azure AI Search, Amazon Kendra와 동등
- Cross-encoder reranking: Cohere Rerank API와 동등 (로컬에서!)
- HyDE 모드: 최신 연구 결과 적용

## 5. GTM 전략 제안

### 5.1 즉시 착수 (0~3개월)

#### Anchor Customer 전략
```
목표: 공공기관 1곳 + 제조기업 1곳 레퍼런스 확보

공공기관 후보군:
  - 지자체 (시청, 도청): 조례/규정 검색 AI → 담당자 1명이 결정
  - 공공기관 (공단, 공사): 내규 검색 자동화 → 법무팀 Pain Point
  - 군 (국방부 산하): 매뉴얼/교범 검색 → 폐쇄망 필수 요건 충족

제조기업 후보군:
  - 중견 제조 (500~2,000명): ERP/MES 연동 전 1단계 도입
  - 품질/안전팀: ISO 규정, SOP 검색 자동화 → HWP 사용 多
```

#### Use-case 패키지 정의

| 패키지 | 대상 | 핵심 기능 | 가격 레인지 |
|--------|------|-----------|------------|
| **규정 검색 AI** | 공공기관, 금융 | 내규/법령 Q&A + 출처 표시 | 연 3,000~5,000만원 |
| **품질 매뉴얼 AI** | 제조 | SOP/작업지시서 검색 | 연 2,000~4,000만원 |
| **계약서 분석 AI** | 법무, 구매팀 | 계약 조항 비교/검색 | 연 4,000~8,000만원 |

### 5.2 Partner-Led 전략 (3~6개월)

```
직접 영업 → 실패 확률 높음 (공공: 조달, 제조: 구매팀 프로세스)

권장 채널:
  1. SI 파트너 (삼성SDS, LG CNS, SK C&C 계열)
     → 기존 고객사 인프라에 BAIKAL 번들
     → 수익 배분: 구축비는 SI, 라이선스는 BAIKAL

  2. 보안 솔루션 업체 (안랩, 시큐아이)
     → 망분리 솔루션에 AI 기능 번들
     → 기존 공공 채널 활용
```
